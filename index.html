Updating vulnerable packages often required other changes first: replacing old frontend tooling, fixing CI failures, or changing how releases were built.

01 FRONTEND

Replace obsolete
dependencies.

I upgraded the frontend server’s Kubernetes client and removed vulnerable dependency chains, resolving six CVEs. I also replaced Create React App with Vite and Vitest, moved API generation to OpenAPI Generator, and upgraded the component library.

Six frontend server CVEs resolved ↗CRA → Vite & Vitest ↗Deterministic API generation ↗

02 CI

Get dependency
PRs merged.

Dependency PRs were getting stuck behind flaky tests, failed image builds, and gaps in validation. I worked on those failures, expanded Dependabot coverage, and improved the checks needed to move toward automatic merging.

Dependency validation & auto-merge safety ↗Repository-wide Dependabot coverage ↗API test sharding ↗

03 RELEASES

Check releases
before publishing.

I built release checks around the exact source revision, Python packages, and container images being published. Releases must have zero fixable vulnerabilities unless a finding has an explicit, reviewed exception for that release.

Release automation with kfpr ↗Release image scanning ↗Release-specific exceptions ↗

RELEASE RESULTS

The 2.17.3 release had zero scanner-reported fixable findings across 24 image/platform combinations. Python 3.9 dependencies retained exceptions. 2.18.0 also documented accepted findings in some dependencies and upstream images.

04 / RELEASE 2.18.1

SDK security
fixes for 2.18.1.

Release retrospective

The follow-up work on the 2.18 branch addressed two SDK problems: local condition outputs could execute code on the host, and automatic credential selection could override explicitly supplied credentials.

I submitted the local condition evaluation fix and its 2.18 backport, as well as the credential-selection backport.

This retrospective assumes 2.18.1 has been released. The source data was collected on November 4, before its release was confirmed.
